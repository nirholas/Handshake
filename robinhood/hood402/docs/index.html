01 / THE HANDSHAKE · four states

Four HTTP states.
No redirect, no invoice.

x402 is HTTP the way it was specified: the server answers a paid resource with 402 Payment Required and the terms, the client attaches proof of payment in a header and retries, the server verifies, settles, and returns 200 with a receipt. hood402 is that loop for USDG on Robinhood Chain, spec-conformant, so it talks to any standard x402 client, not just its own.

02 / WHY EIP-3009 · and how we know

USDG hides the
gasless path. We found it.

USDG (Paxos Global Dollar) is a diamond-router token, its base implementation doesn't advertise EIP-3009. But getFacet(bytes4) proves the transferWithAuthorization facet is registered, and the reconstructed EIP-712 domain matches the live DOMAIN_SEPARATOR() byte for byte, on both networks. So settlement is the standard gasless path, the same mechanism USDC uses, the one x402's exact scheme is built around. No custom scheme, no proxy, no Permit2 fallback.

03 / WIRE IT · server & client

One middleware.
One paying fetch.

A paid endpoint is a wrapper. A paying agent is a drop-in fetch. Both sides speak the same spec, so either can talk to anyone else's.

S / SERVER · charge for a route
// express, one route, priced in USDG import { paywall } from 'hood402/server' app.get('/premium', paywall({ price: '0.01', // USDG payTo: '0xYourAddress', network: 'robinhood', // chain 4663 facilitator: 'https://…', }), (req, res) => { res.json({ data: 'unlocked' }) })

No facilitator? Pass a viem wallet + reader and the server verifies and settles locally. Hono works too via honoPaywall.

C / CLIENT · pay every 402 it hits
// the 402 is paid automatically, under a cap import { Hood402Client, fromAccount } from 'hood402/client' const client = new Hood402Client({ signer: fromAccount(account), maxSpendPerOrigin: '1.00', // hard cap, USDG }) const res = await client.fetch(url) // fetchWithReceipt(url) also returns the // decoded X-PAYMENT-RESPONSE settlement

The client refuses to sign above maxSpendPerOrigin before any network call. In the browser, build the signer from an injected wallet with fromWalletClient.

exact / EIP-3009
The only scheme. Every payment is a signed transferWithAuthorization, the payer's signature fixes amount and recipient; the facilitator can only choose whether to broadcast, never what.
verify → settle
A pure state machine: structural checks → signature recovery → on-chain replay guard → balance → broadcast. Every failure has a canonical InvalidReason and human text.
facilitator
A standalone, self-hostable service, /verify, /settle, /supported, /metrics, an idempotent SQLite ledger, a Dockerfile. It never holds user funds.
tested
The exact/EIP-3009 state machine is pinned by 65 tests; the facilitator adds 18 more for ledger idempotency and its HTTP endpoints. npm run e2e proves the full loop against live chain state.
04 / ROBINHOOD CHAIN · both networks

Two networks.
One 6-decimal dollar.

Both are USDG with EIP-712 domain name="Global Dollar", version="1". Aliases (robinhood-chain, eip155:4663, the bare chain ids) all resolve to the same two via resolveNetwork().

two-layer replay guard
A random 32-byte nonce checked against on-chain authorizationState, plus the facilitator's SQLite ledger claiming an idempotency slot on (network, payer, nonce) before broadcast, a retried settle returns the original tx, never a double-spend.
short validity windows
300-second default signing window, a leaked signature has a narrow blast radius.
keys are env-only
The gas wallet and any payer key are env vars, never hardcoded, never logged. The payer needs USDG, not gas.
